# Проверенный запуск YAxUnit через MCP

Для адресных проверок и полного регресса используется `run_yaxunit_tests`.
Параметры запуска клиента и временные файлы формирует сам инструмент.

```json
{
  "project_name": "МояКонфигурация",
  "tests": ["Тесты_Хранение.Сохранение", "Тесты_Форма.ПовторноеОткрытие"],
  "expected_contexts": {
    "Тесты_Хранение.Сохранение": "Сервер",
    "Тесты_Форма.ПовторноеОткрытие": "КлиентУправляемоеПриложение"
  },
  "timeout_s": 600
}
```

`tests` содержит точные имена ожидаемых выполнений. Для параметризованного
метода указываются полные имена случаев из JUnit; в фильтр регистрации
инструмент самостоятельно передает имя метода без параметров. Не включайте
в перечень сценарии, которые не разрешено выполнять в выбранном стенде.

Список модулей `filters` сохранен. Для этого режима можно передать
`expected_count`, но точная сверка имен предпочтительнее одного количества.
Если указаны и модули, и точные тесты, их состав должен совпасть.
Запуск всех тестов без фильтра требует явного `allow_all_tests: true`.

Инструмент проверяет входные параметры до запуска процесса. Он получает базу
и версию клиента из EDT, задает управляемый режим и TESTMANAGER, проверяет
единственную команду запуска и использует ASCII-путь для передаваемого 1С
файла настроек. Кириллическое имя рабочей области не требуется менять:
для служебных файлов используется временный каталог. Если и его путь не
подходит для надежной передачи платформе, процесс не запускается.

Один инструмент не запускает два тестовых клиента одновременно в одной базе.
Прежний файл JUnit не принимается. Отсутствие признака запуска движка в его
журнале ограничено отдельным ожиданием; открытое окно продукта не считается
доказательством выполнения тестов.

После завершения проверяются реальные элементы `testcase`: непустой состав,
имена, повторы, пропуски, ошибки и, если задана карта, контексты. Ошибка или
неполный прогон возвращаются как ошибка MCP. Успех содержит
`tests_verified: true`; полный ответ сохраняется в `result.json` каталога
прогона рядом с конфигурацией, журналами и JUnit.

Доставка расширений остается отдельной явной операцией:
`edt_update_extension` с проверкой родителя, затем ожидание `DONE` и
`updated=true`. Обновление основной конфигурации флагом `update_database`
не заменяет доставку тестового расширения. HTTP-фикстуры, проверка данных и
исходников продолжают работать в постоянной оснастке проекта; транспорт
запуска тестов должен обращаться к этому MCP-инструменту.
