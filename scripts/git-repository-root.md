# Корень Git при устаревшей привязке EDT

`git_inspect` и существующие операции `git_mutate` должны работать в репозитории,
который Git обнаруживает из выбранного пути проекта. Кэш EDT/EGit может указывать
на внешний репозиторий после создания вложенного. Такое состояние нельзя считать
разрешением выполнять команду в родительском репозитории.

`GitService` получает корень через `git rev-parse --show-toplevel` перед операцией.
Отказ Git или пустой результат не заменяются кэшированной привязкой. Сохраняются
явный выбор проекта, относительные пути, родительский репозиторий для проектов
без собственного Git и связанные рабочие деревья с файлом `.git`.

## Повторяемая проверка

`GitRepositoryRootTest` выполняет настоящие команды Git в одноразовых каталогах
JUnit. Проверяются вложенный репозиторий, его подкаталог, относительный путь,
проект без своего репозитория, связанное рабочее дерево, изоляция индекса при
добавлении и отказ для каталога вне репозитория.

Для проверки исходного дефекта `scripts/run-git-root-eval.py` добавляет перед
библиотеками EDT небольшую заглушку `GitUtils`: она возвращает устаревшую привязку
к родителю. Сами `GitService` и Git CLI не подменяются. Один и тот же тестовый код
запускается против прежних и исправленных классов ядра:

```text
py -3.14 scripts/run-git-root-eval.py --tree REPOSITORY --runtime CLASSES \
  --edt EDT_HOME --jdk JDK_HOME --output RESULT_DIRECTORY
```

Для прежней реализации ожидаются шесть падений из семи: пять неверных маршрутов
и отсутствие отказа вне репозитория. На исправленной проходят все семь. Сводка,
полные журналы, параметры компиляции и запуска сохраняются в каталоге результата.
Сборка классов выполняется отдельно; сценарий не переписывает производственный
код и не копирует его логику в тест.

Это проверка поведения сервиса с моделируемым состоянием кэша. Установленный
плагин дополнительно проверяется исходным вызовом `git_inspect` в настоящем EDT.
