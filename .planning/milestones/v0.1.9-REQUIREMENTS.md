# Requirements — v0.1.9 EDT Extension Native Migration Tooling

## Scope

Address the 10 tooling defects/limitations reported by the 1C agent while moving `аи_Артель` objects from the base `ДО` configuration into the `ДО.Артель` extension. The milestone focuses on product tooling in CodePilot1C, not on manually finishing that one migration by editing XML.

## Requirements

### EDTEXT-01 — Extension adoption diagnostics and Bot support boundary

`extension_manage(adopt)` / `extension_adopt_object` must either adopt supported object kinds including `Bot`, or return an explicit machine-readable unsupported-kind response.

Acceptance:

- `Bot.<Name>` lookup is handled consistently with `MetadataKind.BOT` and `create_metadata(kind=Bot)`.
- If EDT `ModelObjectAdopter` cannot adopt Bot, the tool returns `UNSUPPORTED_KIND`/equivalent payload with `kind=Bot`, not `METADATA_NOT_FOUND`.
- Adopt/list code uses one canonical kind-to-configuration collection map, so future top-level kinds do not drift.

### EDTEXT-02 — Generic TypeDescription mutation primitive

Tools must be able to set `TypeDescription` containment fields on existing and newly-created metadata objects.

Acceptance:

- `create_metadata(kind=Constant, properties.type=Boolean)` creates a usable typed constant.
- `update_metadata` can set `type` / `commandParameterType` using simple strings, arrays of type strings, or `{types:[...]}` payloads.
- Type resolution reuses existing `TypeProviderService` / `TypeItem` pre-resolution and qualifier logic where possible.
- Invalid types fail with deterministic `INVALID_PROPERTY_VALUE` including the field name and unresolved type.

### EDTEXT-03 — Validation exposes extension effective names/FQNs

Before mutation, `edt_validate_request` must show the effective name/FQN that will be used in an extension project with automatic prefixing.

Acceptance:

- Create validation response contains `requestedName`, `effectiveName`, `requestedFqn`, `effectiveFqn`, and `autoPrefixed=true/false` for top-level create operations.
- `create_metadata` result echoes the same effective name/FQN.
- Optional guard `allow_auto_prefix=false` is rejected during validation if prefixing would occur.

### EDTEXT-04 — CommonCommand module artifact semantics

Common command modules must materialize and be recognized as `CommandModule.bsl` / command module contexts.

Acceptance:

- `ensure_module_artifact(module_kind="command")` is accepted for `CommonCommand` and creates/finds `src/CommonCommands/<Name>/CommandModule.bsl`.
- `module_kind=auto` resolves to `CommandModule.bsl` for `CommonCommand`, not `Module.bsl` or `ObjectModule.bsl`.
- `bsl_module_context` for CommonCommand command module reports command-module semantics and no longer causes client/server pragmas to be diagnosed as common-module errors.

### EDTEXT-05 — Standard command group aliases and candidates

Command group fields must accept standard groups in both short and fully-qualified forms.

Acceptance:

- `update_metadata(... group="FormCommandBarImportant")` and `group="StandardCommandGroup.FormCommandBarImportant"` both resolve to the same value.
- `edt_field_type_candidates(field="group")` or an equivalent candidates path returns known `StandardCommandGroup` values for CommonCommand placement fields.
- Unknown groups fail with available-values hint.

### EDTEXT-06 — Extension role/config rights diagnostics

Role-right mutation in extension projects must report whether configuration-level rights are supported and, if so, which values are available.

Acceptance:

- `mutate_role_rights(set_config_right ThinClient)` in extension project either works or returns `UNSUPPORTED_IN_EXTENSION` with available config rights.
- Errors include `project`, `role`, `right`, `targetKind=Configuration`, `isExtensionProject`, and an `availableRights` list.
- The behavior is covered by service-level tests with a fake/controlled `IRightInfosService`.

### EDTEXT-07 — Clone/migration plan for complex metadata objects

The product must provide a high-level dry-run-first migration capability for native extension analogs.

Acceptance:

- New migration planner can inspect source object structure for InformationRegister, Catalog, HTTPService, CommonCommand, ScheduledJob, Bot, Role, and form/module artifacts.
- Dry run emits ordered operations, effective names/FQNs, unsupported fields, reference rewrites, and required validation tokens/confirmations.
- Apply mode creates native extension objects with children, types, modules, forms where supported, and deterministic skipped/unsupported sections where not yet supported.
- Source deletion remains out of scope unless explicitly confirmed after successful clone verification.

### EDTEXT-08 — Regression tests and EDT smoke proof

Each reported failure class must have automated or smoke verification.

Acceptance:

- Unit tests cover: Bot adoption lookup/unsupported diagnostics, Constant type create, commandParameterType update, extension prefix validation, command module path resolution, standard group aliases, and role config-right diagnostics.
- Tool schemas remain strict/Qwen-compatible for new/changed tools.
- Full reactor build command is documented for release delivery: `mvn -DskipTests package`.

## Future Requirements

- Full deletion/move workflow that removes base objects only after verified extension-native replacements and user confirmation.
- Complete semantic reference rewriting inside arbitrary BSL modules; this milestone may start with metadata references and explicit copy lists.
- Visual migration wizard UI. CLI/tool API comes first.

## Out of Scope

- Manual `.mdo` XML patching as the main migration mechanism.
- Changing EDT platform behavior or suppressing valid SU diagnostics instead of creating the correct module type/path.
- Releasing/publishing the update site during planning; release is a later execution/ship activity.
