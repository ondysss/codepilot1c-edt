# Plan 02-01 — Low-level EDT tooling fixes

## Tasks

<task id="02-01-T1" title="Canonical top-level kind collection">
Make extension source lookup/listing use one canonical kind-to-configuration collection path. Include Bot when available in the EDT compile target; otherwise fall back to reflective/feature-based discovery and explicit `UNSUPPORTED_KIND` if adoption fails.
</task>

<task id="02-01-T2" title="Reusable TypeDescription mutation helper">
Implement a shared helper accepting scalar string, list/array, and `{types:[...]}` payloads. Reuse existing `TypeProviderService`/`TypeItem` resolution and qualifiers; apply to Constant `type`, CommonCommand `commandParameterType`, and current BasicFeature paths without regression.
</task>

<task id="02-01-T3" title="Effective extension name validation">
Move extension effective-name/FQN calculation into validation output. Add `allow_auto_prefix` normalization/validation and make `CreateMetadataTool` use the validated effective name instead of recomputing divergent behavior.
</task>

<task id="02-01-T4" title="CommonCommand command module artifact">
Add `COMMAND` module artifact kind (`command`, `commandmodule`, `command_module`). For CommonCommand, make `AUTO` and `COMMAND` use `CommandModule.bsl`; reject `COMMAND` for incompatible owner kinds with a clear error.
</task>

<task id="02-01-T5" title="StandardCommandGroup aliases and candidates">
Accept both `FormCommandBarImportant` and `StandardCommandGroup.FormCommandBarImportant`, and surface available values for unknown group values.
</task>

<task id="02-01-T6" title="Extension role/config-right diagnostics">
Detect extension projects through gateway/project-manager helpers. On unavailable config right, return structured unsupported/available-rights information instead of bare `METADATA_NOT_FOUND`.
</task>
